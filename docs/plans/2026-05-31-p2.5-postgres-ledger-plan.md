# P2.5 — Postgres deploy ledger + ingester implementation plan

**Goal:** Give maki a durable deploy ledger in its **own dedicated Postgres** (decision recorded in
`docs/ARCHITECTURE.md` §9) so reads are instant (background precompute), history survives restarts
and reaches past live ECS retention, and actions can later be recorded — unblocking rollback count,
change-fail rate, drift flag, and Actions run links.

**Architecture:** A SQLAlchemy-modelled `deploy_events` table in a separate Postgres instance. A
background ingester periodically snapshots ECS revisions + Amplify + GitHub enrichment and upserts
events idempotently. Metrics/history/activity reads repoint from the live per-request AWS fan-out to
the ledger. The ingester becomes the sole AWS caller for deploy history.

**Tech stack:** Postgres, SQLAlchemy 2.x, Alembic (standalone — maki's own alembic in `backend/`,
NOT pants/monorepo tooling), pydantic-settings, FastAPI lifespan for the background task.

**Hosting context:** hosted ephemeral container → DB is external; `DATABASE_URL` config; local dev
Postgres via `docker compose`.

**Stack / sequencing (each its own ship-flow task + local commit; migration in its own commit):**

---

## Task 1 — DB scaffolding + first migration (schema only, ledger unused)

Self-contained foundation. NO read/behavior change yet — just stand up the DB layer + schema so later
tasks have something to write to/read from.

**Files:**
- `backend/requirements.txt` — add `sqlalchemy`, `alembic`, `psycopg[binary]` (psycopg3). Follow the
  repo's existing dependency style; pin loosely like the existing entries.
- `backend/src/maki/settings.py` — add `database_url: str = "postgresql+psycopg://maki:maki@localhost:5544/maki"`
  (env-overridable `DATABASE_URL`). Use port **5544** locally to avoid clashing with any existing
  Postgres on 5432.
- `backend/src/maki/db/__init__.py`
- `backend/src/maki/db/engine.py` — SQLAlchemy `engine` + `SessionLocal` (sessionmaker) built from
  `settings.database_url`; a `get_session()` contextmanager/dependency.
- `backend/src/maki/db/models.py` — declarative `Base` + `DeployEvent` model:
  - `id` (int PK), `service` (str, indexed), `platform` (str: "ecs"|"amplify"),
    `revision` (int, nullable — Amplify has none), `sha` (str|null), `image` (str|null),
    `registered_at` (timezone-aware datetime, indexed), `committed_at` (datetime|null),
    `author` (str|null), `message` (text|null), `commit_url` (str|null), `pr_url` (str|null),
    `ingested_at` (datetime, server_default now()).
  - Unique constraint for idempotent upsert: `UniqueConstraint(service, revision)` named
    `uq_deploy_event_service_revision` (Amplify rows, revision NULL, fall back to a second unique
    `(service, sha)` partial — or, simpler for now: ingest ECS only in T2 and leave Amplify for
    later; model the column nullable regardless).
  - Composite index `(service, registered_at)` for date-range reads.
- `backend/src/maki/db/repository.py` — thin `DeployEventRepository` with the methods the later tasks
  need (stubs are fine now, but implement what's trivially testable): `upsert_many(session, events)`
  (idempotent on the unique key via PG `ON CONFLICT DO UPDATE`), `list_for_service_since(session,
  service, since)`, `list_services(session)`. Keep SQL in the repository; services never touch the
  session directly.
- **Alembic setup** in `backend/`:
  - `alembic init` (or hand-place a minimal `alembic.ini` + `migrations/env.py`) wired to
    `settings.database_url` and `db.models.Base.metadata` for autogenerate.
  - **Generate** the first migration with `alembic revision --autogenerate -m "create deploy_events"`
    — do NOT handwrite the revision. Verify the `upgrade()` creates the table + indexes + unique
    constraints; edit only if autogenerate missed something.
- `docker-compose.yml` at repo root — a `postgres:16` service named `maki-postgres`, exposing
  `5544:5432`, env `POSTGRES_USER=maki POSTGRES_PASSWORD=maki POSTGRES_DB=maki`, a named volume.
- `backend/tests/db/__init__.py`, `backend/tests/db/test_repository.py`:
  - A pytest fixture that connects to the local Postgres (`DATABASE_URL`/the compose service),
    creates tables (run migrations or `Base.metadata.create_all`), and wraps each test in a
    transaction rolled back at teardown.
  - Tests: `upsert_many` inserts; re-`upsert_many` with the same `(service, revision)` updates rather
    than duplicating (assert row count stable, fields updated); `list_for_service_since` filters by
    `registered_at`; `list_services` returns distinct sorted names.

**Verification:**
- `docker compose up -d maki-postgres` then from `backend/` (venv): `alembic upgrade head` succeeds;
  `python -m pytest -q` green (DB tests included).
- README/`backend/README.md`: add the `docker compose up -d maki-postgres` + `alembic upgrade head`
  setup steps.

**Commits:** scaffolding (deps, settings, db package, compose, alembic wiring) in one commit; the
generated migration in its OWN commit (mirrors the repo's migration-isolation convention). No push.

## Task 2 — background ingester (ECS + Amplify + GitHub enrich → ledger upsert)

- FastAPI **lifespan** task started on app startup: every `ingest_interval_seconds` (settings,
  default e.g. 300), snapshot all ECS service families' task-def revisions + Amplify current, enrich
  via `GitHubEnricher`, map to `DeployEvent`s, `upsert_many`. Idempotent — safe to run repeatedly.
- Reuse `ECSDeployRegistry`/`ECSDeployHistory`/`AmplifyDeployRegistry`/`GitHubEnricher`. Bound the
  per-run work (since last-ingested or a rolling window) to avoid re-describing all history every run.
- Robust: one service failing must not abort the run; log + continue. Reuse the sha→commit cache.
- Tests: mocked AWS/GitHub; assert events upserted, idempotency across two runs, failure isolation.

## Task 3 — repoint reads to the ledger

- `HistoryService`/`MetricsService`/`ActivityService` read from `DeployEventRepository` instead of the
  live AWS fan-out. Metrics aggregation runs over ledger rows (cheap SQL or in-Python). Keep response
  schemas unchanged. Inventory (current live state) may stay live or move to a "latest per service"
  ledger query — decide at task start.
- Tests updated to seed the ledger and assert the same response shapes.

## Task 4 — drop redundant per-request AWS fan-out + precompute fold-in

- Remove now-unused live-fetch paths; the ingester is the sole AWS caller for history. Confirm cold
  reads are instant (served from DB). Update `ARCHITECTURE.md` §5/§9/§10 + `BACKLOG.md` (precompute
  now satisfied by the ingester; close or fold the item).
